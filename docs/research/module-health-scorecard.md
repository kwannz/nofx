## 2. 分模块详情

### 2.1 Bitget 实盘交易接口（trader/bitget_trader.go）

**结论**：可用但有缺口，8/10，评估方和质疑方一致。单向模式已在官方 Demo 上跑通下单、止盈止损挂单、交易所侧止损触发和权益对账。HEAD 已改为默认对冲模式，但对冲模式没有端到端实测，也没有在真实资金账户上验证过。

**证据**
- **Demo 运行**（data_demo/data.db 与 backend_demo.log）：
  - 交易员自主下了 8 笔单（5 开 3 平），首次轮询全部 FILLED，没有出现 "order detail query failed"。
  - 交易所侧止损触发 2 次：BTC 触发价 83398、成交 83390.5；ETH 触发价 2568、成交 2567.40。
  - SL 5/5、TP 5/5 挂单成功，从开仓到挂单都在 1s 以内；日志中 "Bitget API error" 为 0 条。
- **费率**：20 笔订单的 commission/notional 全部是 0.0600%，等于 takerFeeRate；手续费合计 2.2491 USDT。
- **对账**：仓位 6–9 毛盈亏 -2.64437（质疑方更正了原报告的笔误 -2.64427），手续费 1.84886，净值 -4.49323；交易所权益从 27857.73 变为 27853.24，差 -4.49。仓位 10 是交易员停止后通过 API 平掉的 BTC 空单（净 -0.354），不在对账范围内。
- **公共 API 探针**（go -overlay，未下单）：
  - BTC/ETH/NVDA/XAU 合约解析正确，XAU 和 NVDA 的 isRwa=true。
  - 数量按步长向下取整：0.004789834→0.0047，0.097207→0.09，0.155458→0.15。
  - NVDA 0.01 张折合 2.37 USDT，低于 5 USDT 最小值，被正确拒绝；未知合约返回 40034。
- **测试**（HEAD f261891）：
  - `go test -short -v -run Bitget ./trader/`：69 个顶层 PASS（含子测试共 202 行 PASS），0 FAIL，1 SKIP（TestBitgetDemoIntegration）。
  - `-race -count=3` 通过，耗时 8.5s。
  - 覆盖率：bitget_trader.go 89.6%（626/699），bitget_order_sync.go 90.0%。较低的函数有 SetMarginMode 52.9%、inferBitgetCloseType 42.9%、NewBitgetTrader* 0%。
  - 真实抓包共 48 份，其中 44 份被测试引用。

**问题（按严重度）**
- **中**（质疑方补充）：下单请求到达交易所后若响应丢失（30s 超时、连接重置、5xx），placeMarketOrder 直接返回错误。它生成的 clientOid 从来不用于回查订单。AutoTrader 随后把这次开仓当作失败，跳过 SL/TP 设置，结果可能留下一个已成交、没有记录、也没有止损的仓位。另外遇到 429 也不会重试。
- **中**：开仓成功后如果 SL/TP 设置失败，只记一条日志：不重试、不核验、也不紧急平仓。confirmOrder 在 3 次 300ms 轮询后可能仍返回 NEW，后续流程照常继续。
- **中**：availableBalance 没有扣除持仓保证金。Demo 上 available 一直是 27857.27，而实际占用保证金约 254 USDT；16:16:59 时 available 甚至高于 equity。在小账户上可能触发 43012/40762 错误。
- **中**：单向模式下反向开仓没有保护（paper 有）。HEAD 默认对冲后，只影响主动选择 one_way 的用户，或切换模式被拒的账户。
- **低**：平仓归因丢失。CloseType 恒为 unknown，close_reason 全是 sync。9f861d0 的 close_reason 修复没有覆盖 Bitget 实盘。
- **低**：几处记录与实际不符：
  - DB 中杠杆恒为 1，实际是 3x。
  - exchange_order_id 存的是 tradeId，不是 orderId。
  - 决策记录里 order_id 恒为 0。
  - 决策记录存的是请求数量而不是成交数量（0.004789834 对 0.0047）。
- **低**：按步长向下取整让小单缩水 1.9%–7.4%（BTC/ETH/XAU）。
- **低**（质疑方补充）：同步窗口固定为最近 24h、最多 10 页；停机超过 24h 期间的成交永远不会导入。同步 goroutine 无法停止，详见 2.2。
- **低**：以下路径只有 mock 验证：止盈触发（Demo 中 0/5）、cancel-plan 响应、带持仓时 SetMarginMode、部分成交、NVDA RWA 下单；也没有 accounts 抓包。
- **低**：
  - e2e 证据只覆盖单向模式，而单向现在已不是默认。
  - 4 份 hedge_* 抓包没有被测试引用。
  - docs/research/paper-trading-validation.md 第 7 节已过期。
  - Demo 账户与集成测试共用，数据被污染。
- **已撤销**：
  - 原报告"不支持对冲模式、每次构造都强制切到 one_way"：f261891 已解决。现在默认 hedge，ensurePositionMode 先 GET 检测、只在不一致时才切换，临时 trader 也会传入已存储的模式。
  - 原报告"已知测试失败"：已由 ae14590 修复。

**建议**
- 下单失败时用 clientOid 回查订单，确认成交就补设 SL/TP。
- placeTPSL 重试 2–3 次，再用 GetOpenOrders/GetPositions 核验；仍然没有止损就告警或平仓。
- 可用余额改用 crossedMaxAvailable，或用 equity 减去各仓位保证金之和；先抓包确认字段。
- 单向模式开仓前检查是否持有反向仓位。
- 从 GetPositions 或 order detail 回填杠杆和 orderId。
- 用 Demo 补抓 contracts、ticker、accounts、set-leverage、cancel-plan 和 NVDA 订单的响应。
- 用一个独立的 Demo 账户跑一次对冲模式全流程。

### 2.2 订单同步与持仓记录（bitget_order_sync.go + store position builder）

**结论**：6.5/10。评估方给 7，质疑方降为 6.5，理由有两条：goroutine 泄漏已经在实盘中发生，而且 Bitget 的手动平仓和回撤平仓恰恰依赖这个泄漏的循环；面向 AI 的数据缺陷是真实存在的。单交易员独占账户的正常路径记账是精确的。

**证据**
- 成交 20/20 入库，0 个重复 tradeId，订单与成交 0 处不一致。10/10 个已平仓位的 realized_pnl 与 方向×(出场价−入场价)×数量 差为 0，手续费差 <1e-6。
- **余额对账**：仓位 6、7、8 的净值 -2.79285218，减去 ETH 开仓费 0.2318085，得 -3.02466068；权益快照余额差为 -3.02466069。
- **同步次数**：日志共 106 次（16:11:28–17:03:59），0 错误。其中 62 次在交易员运行期间，44 次在 16:41:59 停止之后；原报告的 72 次是日志还在增长时的快照。
  - 有新成交的批次共 7 次，合计 20 笔（10+2+3+1+1+2+1），最后一批来自停止后的循环。
  - 成交到入库的延迟：最短 1.6s，中位约 8.6s，平均 11.2s，最长 27.3s。
- **毛利与净利**：10 个仓位毛利 -2.64797，手续费 2.2490539，净值 -4.8970239。按毛利算胜 3/10，按净利算胜 0/10。
- **质疑方补充**：每个仓位都只有 1 笔开仓成交加 1 笔平仓成交，所以均价合并、部分平仓、多笔成交订单都没有实盘覆盖。原报告"账户已平"的结论只是 DB 内部一致，不是交易所侧的核验。
- **测试**（HEAD 4453958）：
  - 测试计数：73 PASS / 6 SKIP。
  - 覆盖率：SyncOrdersFromBitget 86.5%，classify* 100%，StartOrderSync 0%，handleOpen 50%。
  - position_builder_test.go 有 4 个测试，但只测 close_reason。
- **探针**（在 HEAD 上复现）：
  - 1200 笔成交只存下 1000 笔。
  - 同一毫秒的开仓和平仓会留下一个幻影 OPEN 仓位。
  - 存在陈旧的 OPEN 多单时，一笔真实空单会被算出 pnl=100，而真实值是 +1.0。
  - 第二个交易所记录拿到 0 笔订单，并持续报 UNIQUE 冲突。

**问题（按严重度）**
- **高**：共享账户和多交易员处理有误。
  - 同步会导入账户最近 24h 的全部成交，不区分归属。Demo 库中 10/20 笔成交、5/10 个仓位其实来自之前的集成测试。
  - 唯一索引实际只建在 exchange_order_id、exchange_trade_id 单列上（gorm 标签缺 priority:1）。第二个交易员因此拿不到任何成交，还会持续报 UNIQUE 冲突。
- **中**（质疑方加强）：同步 goroutine 没有停止通道，实盘中停止后又多跑了 44 次。
  - Bitget 的手动平仓和回撤紧急平仓是故意交给 OrderSync 记录的：仓位 10 就是靠停止后的循环在 16:42:29 才入库。所以如果只修 Stop()，交易员停止期间发生的平仓就不会入库。
  - 去重按 exchange_id 而不是 trader_id。删除或编辑交易员后，新旧两个循环会互相竞争。
- **中**：持仓分类依赖 DB 中的 OPEN 行，而且不与交易所持仓对账（CreatePositionSnapshot 和 SyncClosedPositions 都没有调用者）。陈旧的 OPEN 行会伪造出盈亏。这个问题主要影响单向模式。
- **中**：realized_pnl 是毛利，胜率、Sharpe 和给 AI 的 RecentTrades 都基于毛利；资金费没有记录。这是全系统的口径问题，不是 Bitget 特有的。
- **中**：同步生成的仓位 leverage 恒为 1，导致 pnl_pct 被低估 3 倍。例如 #8 显示 -0.18%，按 3x 应为 -0.54%。
- **中**：close_reason 恒为 sync。HEAD 前端已经渲染 CloseReasonBadge，所以 Bitget 实盘的所有平仓（AI、手动、回撤、SL、TP）在 UI 上都显示 sync，而 paper 能显示真实原因。
- **低**：
  - 24h 窗口加 1000 条上限，超出部分静默丢弃。
  - 同毫秒成交排序不稳定（sort.Slice），会产生幻影 OPEN。
  - 数量容差 0.0001 太粗，价格四舍五入到 2 位小数。
  - 手续费解析假设币种是 USDT 并取绝对值。
  - 订单、成交、仓位写入不在同一个事务里。
  - 首次同步在 Run 之后 30s 才执行。
- **低**（质疑方补充）：单向模式下反向开仓如果造成翻仓，超量平仓部分会被截断，新的反向腿不会入库。这是代码分析结论，未实盘验证。
- **HEAD 已修复**：对冲模式平仓成交的 side 规范化问题（f261891）。

**建议**
- 唯一索引改为 (exchange_id, …) 复合索引，并写迁移重建；导入时按交易员归属过滤（启动时间、自身 orderId、配置的 symbol）。
- 给 StartOrderSync 加上 stop context，同时让 Bitget 的手动平仓和回撤平仓即时记录。
- 启动时和周期性地与 GetPositions 对账。
- 新增 net_pnl，并在统计和 AI 上下文中使用它。
- 杠杆从交易所数据写入；按 orderSource/tradeSide 推导 close_reason。
- 持久化同步游标，碰到页数上限时告警。
- 排序改用 SliceStable，并按 tradeId 打破平局。

### 2.3 Bitget 行情源（provider/bitget + market/source.go）

**结论**：8/10。评估方给 8.5，质疑方降为 8，原因有三：结构化的问题清单里有一条是占位符；"1044/1044"只覆盖了 105 条提示词中的 2 条；另外发现了 3 个小缺口。数据保真度高，实测零失败。

### 2.10 外部数据源（nofxos / CoinAnk / Binance 回退）

**结论**：6/10。评估方给 6.5，质疑方降为 6：三个数据源里，nofxos 交付 0% 的数据，Binance 在此环境被地域封锁，模块的实际价值全部来自 Bitget 路径；质疑方还发现了 key 泄漏等缺陷。Bitget 交易员的行情链路是可靠的；依赖 nofxos 的默认配置和功能是坏的。

**证据**
- **nofxos 现状**：内置公共 key 返回 HTTP 402（两次实测：17:35:15 UTC 和 18:19:56 UTC），响应体会回显完整 key。
- **旧二进制**（40dd38d，早于熔断器提交 b88b888）：1529 次失败调用，覆盖 110 个周期，成功 0 次；"NofxOS API disabled" 出现 0 次，说明熔断器从未在完整运行中生效。
- **HEAD 探针**：
  - 第 1 个周期 nofxos 失败 1 次后熔断，之后 0 次 HTTP 请求。
  - 3 个周期共 73 个请求，全部发往 api.bitget.com。
  - strace 只看到 1 次到 nofxos 的连接。
- **source=default 对比**（质疑方复跑）：Binance 返回 451，导致 BTC/ETH/XAU 的 OI 为 0，被流动性过滤掉；NVDA 经 Hyperliquid 豁免而保留。原报告说"全部被过滤"，没有复现。
- **默认 ai500 配置**：探针显示每个周期都以 "failed to request AI500 API: nofxos: API unavailable" 中止。
- **提示词**：105/105 条系统提示仍宣称有"量化数据（机构/散户资金流）"，而没有任何一个周期真正拿到。
- **测试**：熔断器 9/9、门控 7/7 通过；但熔断器测试用的是 HTTP 200，而不是真实的 402。

**问题（按严重度）**
- **高**：默认策略的币种来源是 ai500，依赖已废弃的 key。用默认配置创建的交易员，无论哪个交易所，每个周期都会中止。e2e 能跑通，只是因为脚本改成了静态币表。
- **中**：资金流、OI 排名、价格排名这些数据永久缺失，也没有替代来源；系统提示仍宣称有这些数据；UI 不显示 nofxos 不可用。
- **中**（质疑方补充）：
  - key 放在 URL 查询参数里，任何传输错误都会把完整 key 写进日志（已复现）；上游的错误响应也会回显 key。所以"换成付费 key"这个修复方案，会在第一次网络错误时把付费 key 泄漏出去。
  - 回测和辩论使用 DefaultClient 的硬编码废弃 key，忽略用户在策略中配置的 key。
- **中**：熔断器从未在完整运行中验证；策略试运行、辩论、回测这些路径不按交易所选择数据源。
- **低**：
  - 遥测默认开启，会上报每笔交易（user_id、trader_id、金额、杠杆）。
  - 熔断器靠匹配错误文案识别真实的 402，上游一改措辞就失效。
- **低**（质疑方补充）：
  - 排名接口在非 key 类失败时返回空结构且不报错，提示词里出现空的标题段落。
  - 熔断器不处理传输层失败；SafeHTTPClient 不读 HTTPS_PROXY，每次调用最长可能阻塞 30s。
  - OI Average 是伪造的（同 2.3）。
  - FetchExternalData 是死代码；启动日志对 Bitget 有误导。

**建议**
- Bitget 默认模板改用静态币表，并关闭量化和排名开关；ai500 在 nofxos 不可用时回退到静态列表。
- key 改为请求头传递，所有日志脱敏；回测和辩论改用策略中配置的 key。
- 提示词按数据的实际可用性生成；状态接口暴露 nofxos 是否可用。
- 熔断器把 402 和传输层失败纳入，并用真实的 402 载荷写测试。
- 遥测改为默认关闭。
- 用 HEAD 二进制跑 2–3 个周期复核。
